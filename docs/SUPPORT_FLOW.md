# Поддержка: локальная реализация и проверка

## Реализованный процесс

`active → waiting_operator → operator_assigned → operator_active → waiting_user → resolved`

- Маршрутизация использует содержательный вопрос, четыре последние пользовательские
  реплики, роль и раздел портала. Сохраняются тема, линия, уверенность, правило и причина.
  Низкая уверенность отправляет на первичный разбор консультационной линии. Для внешнего
  адресата чат показывает инструкцию и явно говорит, что автоматической отправки не было.
- Автоназначение выбирает онлайн-сотрудника нужной линии с минимальной нагрузкой.
  По обновлённому требованию пользователя ограничение количества обращений удалено
  из ручного принятия, автоназначения и переназначения.
  Назначение и принятие разделены, таймаут принятия — 60 секунд. Активный диалог из-за
  молчания сотрудника не отбирается.
- Только владелец может отвечать, прикладывать файл, переводить и предлагать решение.
  Перевод требует причину и сохраняет исходное время ожидания. Администратор может
  переназначить сотруднику той же линии с причиной.
- Копайлот показывает сводку, проверки, недостающие сведения, предупреждения, документы
  и черновик. Исторические обращения отделены от инструкций и не вставляются в ответ.
  Ошибки поиска/модели видны явно; первая статья не подставляется как готовый ответ.
  Параллельные генерации одной версии объединяются, опоздавшая помечается устаревшей,
  набранный сотрудником текст не перезаписывается. Использование черновика журналируется.
- `waiting_user` различает уточнение и предложение решения. Только «Помогло» закрывает
  обращение; «Не решено» возвращает прежнему онлайн-сотруднику или в очередь. Молчание
  не закрывает обращение.
- Переходы и уведомления пишутся одной транзакцией через outbox. События имеют ID,
  клиенты устраняют дубли. Повторная отправка сообщения с тем же request ID не создаёт
  копию. Версионный конфликт возвращает 409 и актуальное состояние. Права проверяются
  в HTTP и при каждой доставке в WebSocket-комнату.

## Локальный запуск

Изолированный стек работает в Podman как проект `supportflow`: frontend `8099`, API
`18009`, PostgreSQL `15439`, отдельные Redis/Qdrant и тома. В PostgreSQL скопированы
диалоги, в Qdrant — проиндексированная коллекция БЗ (9046 точек); старые активные
обращения закрыты только в копии, чтобы диспетчер их не назначал.

После явного разрешения пользователя основной локальный API подключён к модели Ollama
(`qwen3.8:27b`). Живые тестовые диалоги и найденные выдержки БЗ используются для ответов
бота и копайлота. Адрес и ключ (`OLLAMA_EVAL_BASE_URL`, `OLLAMA_EVAL_API_KEY`) хранятся
в локальной конфигурации `.env.support-eval.local`, не в Git. Применить настройки повторно можно из корня worktree:
`backend/.venv/bin/python scripts/enable_support_llm.py`.
Отдельный evaluator по-прежнему использует фиксированные обезличенные кейсы.

В compose явно разрешён origin frontend на `8099`: WebSocket операторской
проходит аутентификацию и поддерживает отметку сотрудника онлайн.

Живой браузерный smoke-прогон (`frontend/scripts/support-live-smoke.mjs`) проверяет
первую смешанную фразу «Позовите оператора, как зарегистрироваться на портале?»,
ручной LLM-черновик и автоматический новый черновик после уточнения роли поставщика.
Оба черновика получены от Ollama; проверены WebSocket-доставка, сводка, источники
и сохранение набранного сотрудником текста. Результат: `reports/support-live-ui/result.json`.
Большая подсказка прокручивается в своей панели, сохраняя место для переписки.

Запуск после остановки:

```bash
podman compose --env-file .env.support.local -f compose.support.yml up -d postgres redis qdrant api frontend
```

## Проверки и измерения

- До изменений: 27 выбранных backend-тестов существующего копайлота/очереди/истории.
- После изменений: 103 backend-модуля запускаются изолированно с таймаутом; новые наборы
  покрывают конкурирующее принятие, права линий и владельца, CAS 409, перевод,
  переназначение, работу с более чем тремя обращениями, таймаут 60 секунд, отсутствие автозакрытия, идемпотентность,
  outbox при недоступном Redis, single-flight и устаревший результат.
- Frontend: 43 файла, 242 теста; typecheck и production build проходят.
- Нагрузка передачи в поддержку: 1/3/10 параллельных диалогов — 0 ошибок;
  p50: 164/181/495 мс, p95: 164/181/690 мс. Копайлот запускается фоном и не задерживает
  приём сообщения пользователя.
- Маршрутизация: 303 отложенных примера, 69 близких дублей исключены из обучения,
  порог выбран на отдельной калибровке из 599 примеров. Результат: precision 89,5%,
  coverage 40,9%. Цель 90% при 70% **не пройдена**. Метки получены преобразованием тем
  выгрузки, а не независимой ручной разметкой, поэтому перед релизом нужен ручной gold set.
- LLM: 100 фиксированных диалогов × 3, параллельность 2. Автоматические проверки
  контролируют ссылки на известные документы, отсутствие выдуманных выполненных действий,
  безопасное уточнение при отсутствии данных, конфликт источников и отказ поиска.
  Завершены все 300 прогонов: 58 из 100 диалогов прошли во всех трёх повторах,
  автоматический pass rate — 59,3%, ошибок — 16, p50 — 5,20 с, p95 — 12,50 с.
  Цель 90 из 100 стабильных диалогов **не пройдена**.
  Семантическую полезность и достаточность ответа всё равно должен подтвердить человек по
  указанным документам; оценка той же моделью не используется как единственный судья.
- Браузерный E2E прошёл полный путь с посетителем, двумя сотрудниками одной линии,
  сотрудником другой линии и администратором: гонку принятия, запрет чужих действий,
  ответ, копайлот без перезаписи текста, уточнение, идемпотентность, offline/reconnect,
  перевод, «Не решено», «Помогло» и восстановление истории после reload.

Артефакты: `reports/support-routing/routing.json`, `reports/support-load.json`,
`reports/support-live-v2/summary.json`, `reports/support-e2e/result.json`. Обновлённая схема:
`docs/bpmn/support.bpmn` и `docs/bpmn/support.svg`.

## Блокеры готовности

1. Маршрутизация не достигла согласованного сочетания точности и покрытия.
2. LLM-копайлот не прошёл автоматический порог стабильности; дополнительно требуется
   ручная проверка 100 ответов по эталонам.
3. Локальная Podman VM имеет 8 ГБ RAM без swap; при одновременном полном backend-прогоне,
   сборке и LLM-evaluator был зафиксирован OOM. Тестовые нагрузки следует запускать
   последовательно или увеличить память/swap VM.
