# Синонимы действия в поиске: «выгрузить» = «скачать» = «экспортировать»

Дата: 2026-09-12. Ветка `fix/kb-search-download-synonyms`. Регресс закреплён тестами
`tests/test_querytext.py::test_download_synonyms_are_one_concept`,
`tests/test_retrieval.py::test_download_synonyms_share_a_lexical_token` и тремя новыми
вопросами в `app/seed/golden.json`.

## Проблема

Кнопка «Как выгрузить УПД?» и тот же вопрос, набранный руками, шлют один текст, но
ReAct-агент формулирует повторный поиск каждый раз заново (`app/services/agent.py`,
`search_kb`). Если он ищет «скачать УПД» — находит статью и отвечает; если «УПД выгрузка»
или «экспортировать УПД» — отказывает. Кнопки для этого конкретного вопроса уже заменены
на прод-проверенные формулировки отдельно (`chat.chips*` в `dynamic_settings.py`, не
трогалось). Открытым оставался набранный руками вопрос.

Живой прогон на проде (194.31.175.172, `valerchik-api-1`, прямой вызов
`Retriever.search` в обход агента, четыре запроса) показал причину: не различие в
итоговом score, а то, что нужная статья **вообще не входит в топ-5**.

```
=== query: 'выгрузить УПД' ===
  score=0.655  Q='9.1.1 Выгрузка оферт'                          # не про УПД вовсе
  score=0.509  Q='Как загрузить документ УПД, если он не загружается?'
  score=0.503  Q='Как формируется печатная версия УПД и где её получить?'
  ...                                                             # «Скачать XML» — не в топ-5

=== query: 'скачать УПД' ===
  score=0.651  Q='Где можно скачать XML‑версию УПД?'              # верная статья, первая
  ...
```

«Выгрузка»/«выгрузить» и «скачать» не пересекаются ни одним лексическим токеном:
BM25 отдаёт top-1 статье, вообще не связанной с УПД, только потому что она лексически
точнее совпадает с «выгрузка». «Экспортировать УПД» проваливается ещё хуже — ни один
кандидат из топ-5 не про скачивание вовсе.

## Метод

Синоним действия сведён к одному понятию для лексического индекса — тем же механизмом,
что и сокращения (`_phrase_stems`/`by_start`/`forms` в `querytext.py`), но с
синтетическим ключом `_download`, а не одним из слов группы (см. «Отброшено» — почему
это оказалось важно).

Замер — на золотом наборе (`app/seed/golden.json`, `services/quality.run`, засеянная
синтетическая база, а не прод), при этом расширенном тремя вопросами, которые
перефразируют уже существующие статьи чужими словами из группы синонимов — не только
про УПД, чтобы показать, что чинится поиск в целом, а не один вопрос:

- «где скачать акт сверки» → «**как выгрузить** акт сверки»
- «в каком формате можно **выгрузить** данные для аналитики» → «как **скачать** данные для аналитики»
- «как выгрузить упд» / «хочу скачать упд» / «экспортировать упд для бухгалтера» — юнит-тест на уровне `phrase_concepts`/`index_tokens` (см. тесты)

Держим на 0: `confident_wrong_rate`. Смотрим: `accuracy`/`answer_rate` не ниже текущего
пола (0.53, `test_confidence_golden.py`).

## Отброшено

- **Ключ понятия = одно из слов группы** (как у сокращений: ключ — сама аббревиатура).
  Не сработало: `align_concepts` (используется в `title_match`, а это `TITLE_SHARE=0.75`
  — три четверти веса лексической уверенности) считает конструкцию «ключ + слово, с
  которого начинается основа ключа» за «понятие уже расписано словами», и вычищает
  ключ с обеих сторон как избыточный. Для сокращений это верно (короткая инвариантная
  аббревиатура и её длинная расшифровка лексически не пересекаются, коллизии нет), но
  для группы синонимов ключ **это и есть** одно из слов — совпадение с самим собой
  ложно распознавалось как «расписано полностью», и после вычистки от общего
  токена не оставалось ничего: `title_match("выгрузить упд", "скачать упд")` не менялся
  вообще (0.2330 что с синонимом, что без). Проверено на прямом вызове `title_match` до
  и после — числа совпадали ровно. Решение — синтетический ключ (`_download`), который
  ни с одной основой группы не совпадает.
- **Второй найденный баг по пути, тоже в `align_concepts`.** Даже с синтетическим ключом
  результат не изменился: у алгоритма было ещё одно условие, вычищающее ключ всегда,
  когда обе стороны «расписали понятие словами» — не различая случай «одно и то же
  слово в разных падежах» (тогда сами слова совпадут и без ключа) и случай «разные
  синонимы одной группы» (тогда слова не совпадут никогда, а ключ — единственное общее).
  Функция дополнена третьим случаем: если понятие есть с обеих сторон, расписано
  полностью с обеих сторон, но расписанные слова не пересекаются сами по себе — ключ
  остаётся на обеих сторонах. После этого `title_match` вырос с 0.2330 до 0.3779 на том
  же примере. Старые тесты на сокращения (падежи одного слова, сокращение против
  расшифровки, абрревиатура с одной стороны без пары) проверены — не задеты.
- **Ранжирование в игрушечном тестовом корпусе (5 статей).** Пробовал доказать фикс
  сравнением топ-1 в маленьком `Retriever.search` с искусственным «отвлекающим»
  документом — не получилось честно: в live-примере статья пропадала из топ-5 именно
  из-за низкого idf токена «упд» на масштабе реальной базы (тысячи статей его
  упоминают). В игрушечном корпусе из 5 документов «упд» — редкое слово с высоким idf,
  которое само по себе протаскивает нужную статью в выдачу что до, что после фикса, —
  тест ничего не доказывал бы и был отброшен в пользу прямой проверки `title_match` и
  прогона на золотом наборе.
- **Векторный запрос (`expand_abbreviations`/`normalize_query`).** Не трогался — при
  чтении вызовов выяснилось, что обе функции сейчас мёртвый код: `Retriever.query_forms`
  не вызывает `expand_abbreviations` вовсе, только опечатки правит для обеих форм
  запроса. Расширять нечего, добавлять новую ветку ради этого не стал.
- **Реальные обращения (`kb_eval` на выгрузке СТП).** Отложено: файла `cases.json` с
  честно отложенными реальными обращениями под рукой не было, а таблица golden-набора и
  без него показывает нужное направление изменения. Отдельным пунктом на будущее — когда
  появится свежая выгрузка, прогнать `python -m app.tools.kb_eval run cases.json` до/после
  и сверить `confident_wrong`/`ood_false_answer`/`hit@1`.

## Решение

`app/services/querytext.py`:

```python
SYNONYM_GROUPS: dict[str, tuple[str, ...]] = {
    "_download": ("выгрузить", "скачать", "скачивать", "экспортировать", "экспорт"),
}
```

`_concepts()` сводит эти слова в дерево `by_start`/`forms` наравне с расшифровками
сокращений — они там гости, а не новая ветка кода. `align_concepts` умеет отличать
«то же слово в другом падеже» (ключ снимается, слова совпадают сами) от «разные слова
одной группы синонимов» (ключ остаётся — только он и связывает стороны).

Морфологическое покрытие (проверено `_phrase_stems`/`_fits` напрямую):

| слово группы | основа | покрывает | не покрывает |
|---|---|---|---|
| выгрузить | выгру | выгрузил/выгрузите/выгружать/выгружает, выгрузка/выгрузки | — |
| скачать | скача | скачал/скачали/скачайте | скачивать/скачивание (отдельный член) |
| скачивать | скачив | скачивает/скачиваем, скачивание | — |
| экспортировать | экспортиров | экспортированный и длинные формы | экспортирует (чередование -ова-/-у-), экспортируется (пассив) |
| экспорт | экспор | экспорт/экспорта, экспортирует/экспортируют | — |

Остаточный пробел: «экспортируется» (пассив) не покрывается ни одним членом — принято
как есть, не стоит шестого члена группы ради одной редкой формы; тот же класс
ограничения уже принят в модуле (`COLLOQUIAL_STEMS`, видовые пары).
